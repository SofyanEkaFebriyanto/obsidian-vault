# Dev Log — kenfa-2.0 SMTP Produksi + Investigasi Akses Mobile (2026-08-27)

## Investigasi "HP nggak bisa akses" — takut pelanggan lari ke lapak lain
Founder khawatir pelanggan harus VPN dulu (kayak SSH). **Terbantahkan lewat tes:**
- IP website (`213.210.57.x` / `147.93.77.x`) **≠** IP SSH yang di-null-route ISP (`145.79.14.115`). Blokir ISP cuma kena SSH, bukan web.
- check-host.net (node global, netral dari koneksi kita): homepage **HTTP 200 dari 15 node / 10+ negara** (BG/CY/IL/IN/IR/PT/RS/SE/UA/US). SSL Let's Encrypt valid s/d 30 Okt 2026, HTTP→HTTPS 301, server hcdn.

### ⚠️ KOREKSI — diagnosis IPv6 pertama SALAH (ditarik)
Sempat disimpulkan: "AAAA record ngadat, endpoint IPv6 Hostinger mati → hapus AAAA record". **Itu keliru dan sudah ditarik sebelum dieksekusi.**
- **Confounder**: VPN di mesin dev **tidak me-route IPv6**. `ping6`/`curl -6` ke **google.com & cloudflare.com juga gagal** dari box yang sama — itu sinyal jaringan lokal, bukan tujuan.
- **Uji ulang dari egress kedua**: via Warp SOCKS5 (:51001, punya IPv6 nyata) + `--resolve` dipaksa ke AAAA `test.kenfa.id` → **HTTP 200**.
- Kesimpulan benar: **IPv4 & IPv6 dua-duanya SEHAT. JANGAN hapus AAAA record.**
- `test.kenfa.id` dilayani CDN Hostinger (apex ALIAS `kenfa.id.cdn.hstgr.net`); A/AAAA berotasi round-robin (IP beda tiap query) — normal.

**Pelajaran metode**: jangan simpulkan "endpoint tujuan rusak" dari satu egress. Uji dulu situs kontrol (google/cloudflare) dengan protokol yang sama — kalau kontrol juga gagal, masalahnya jaringan lokal. Baru uji dari egress kedua yang stack-nya lengkap.

## SMTP produksi diaktifkan
Sebelumnya email verify/reset diam. Root cause: config salah + queue nyangkut.

`.env` live (backup `.env.bak-0827-1616`) dibetulkan:
- Hapus baris ganda `MAIL_MAILER=log` (bikin ambigu).
- `MAIL_PORT` 587 → **465**.
- Tambah **`MAIL_SCHEME=smtps`** (SSL implisit — wajib utk 465; tanpa ini gagal connect).
- Typo **`noreplay@kenfa.id` → `noreply@kenfa.id`** (username + from address).
- **`QUEUE_CONNECTION` database → sync**. Krusial: `ResetPasswordNotification` & `VerifyEmailQueued` `implements ShouldQueue`; dengan `database` + tanpa worker (Hostinger shared butuh cron hPanel yang belum ada), email nyangkut di tabel `jobs` selamanya. `sync` = kirim langsung.

Config live terbaca Laravel: `mailer=smtp host=smtp.hostinger.com port=465 scheme=smtps username=noreply@kenfa.id queue=sync`.

## Gotcha SMTP Hostinger (reusable)
- Port 465 = SSL implisit → **wajib `MAIL_SCHEME=smtps`** (587/tls beda mekanisme).
- Username = **full email**, bukan bagian sebelum @.
- `535 auth failed` = password/akun hPanel salah, **BUKAN** config Laravel — cek Email Accounts di hPanel dulu.
- Email transaksional kenfa di-`ShouldQueue` → `QUEUE_CONNECTION=database` bikin nyangkut tanpa worker. Shared hosting: pakai `sync`, atau pasang cron `queue:work` di hPanel.
